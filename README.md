# SemEval Code Detector

A product-oriented extension of **SemEval-2026 Task 13** for detecting whether source code is written by a human or generated by AI, attributing the most likely LLM family, identifying hybrid/adversarial generation styles, and estimating how much of a hybrid snippet appears to be human-written.

> **Status:** Active development. This repository is designed to turn a shared-task style research pipeline into a usable web product and API.

---

## Overview

Generative models can now produce code that looks highly convincing across programming languages, domains, and prompting styles. This project takes the research setting behind SemEval-2026 Task 13 and turns it into an end-to-end application:

- paste a code snippet into a web interface,
- run a unified inference pipeline,
- get a structured authorship report,
- visualize which parts are likely human-written vs AI-generated.

The system is designed around four product questions:

1. **Was this code written by a human or by AI?**
2. **If AI-generated, which model family is the most likely source?**
3. **Is the code fully machine-generated, hybrid, or adversarially human-like?**
4. **If the code is hybrid, how much of it appears to be human-written?**

---

## Key Features

### Research-aligned detection
- **Binary detection**: human-written vs machine-generated
- **Family attribution**: likely LLM family attribution at the **family level**, not exact model fingerprinting
- **Style classification**: human / machine / hybrid / adversarial

### Product-oriented capabilities
- **Code paste UI** for interactive analysis
- **REST API** for integration into other systems
- **Hybrid segmentation** to estimate the human-written portion of hybrid code
- **Line/block highlighting** to show suspected human vs AI regions
- **Uncertainty reporting** for short, noisy, or out-of-distribution snippets

### Designed for extensibility
- Multiple programming languages
- Modular inference services
- Pluggable calibration and thresholding
- Support for future repo-level scanning and batch processing

---

## How It Works

The product pipeline combines the three core tasks with an additional hybrid segmentation module:

```text
Input code
  -> normalize + detect language
  -> run Task A / Task B / Task C predictors
  -> calibrate and merge predictions
  -> if Hybrid: run span-level segmentation
  -> return structured JSON + highlighted spans
```

### Mapping from research tasks to product outputs

| Research component | Product output |
|---|---|
| Subtask A | Human vs AI |
| Subtask B | Likely author family |
| Subtask C | Human / Machine / Hybrid / Adversarial |
| Product extension | Estimated human-written ratio + highlighted regions |

## Model Strategy

This project is built around a **modular ensemble** rather than a single monolithic model.

- **Task A service**: binary human vs AI detection
- **Task B service**: author-family attribution
- **Task C service**: style classification
- **Hybrid service**: line/block-level human-vs-AI estimation for hybrid snippets
- **Calibration layer**: score normalization, uncertainty control, and decision fusion

This design makes it easier to:

- swap backbones,
- compare experiments,
- export checkpoints for serving,
- improve only one part of the system without rewriting the entire pipeline.

---

## Limitations

This project is intended as a **probabilistic detector**, not a guaranteed proof of authorship.

Important limitations:

- **Family attribution is not exact model identification.**
  The system should be interpreted as predicting the most likely **model family**, not a precise generator name.
- **Short snippets are hard to classify reliably.**
  Confidence should be treated cautiously for very short or heavily edited code.
- **Hybrid estimation is approximate.**
  The human-written ratio is an inference based on local patterns, not a ground-truth decomposition.
- **Out-of-distribution inputs may reduce reliability.**
  Performance may drop on languages, domains, or coding styles not represented well in training.
